Memory allocators

Every new, every string, every list grabs memory from the heap, and gives it back later. The allocator behind malloc and free has to find space fast and avoid leaving the heap full of useless little gaps. Allocate and free, and watch the holes appear.

How it works

The free list. The allocator tracks which ranges are free. malloc(n) finds a free block at least n bytes long, carves off what's needed (splitting), and returns its address. free marks it free again. Merging it with free neighbours (coalescing) stops the heap shattering into ever-smaller pieces. Untick it to see what happens without.

Which hole? First fit takes the first hole that's big enough, which is fast. Best fit takes the tightest fit, saving big holes for big requests but leaving slivers too small to use. Worst fit takes the biggest hole so the leftover stays useful, and in practice usually does worst.

Fragmentation is the real enemy: plenty of free memory in total, yet no single hole big enough. Press "Make Swiss cheese", then try to allocate 10 bytes. There's 64 bytes free, and it still fails. The garbage-collected languages solve this by moving objects to compact the heap, which C's malloc can't do because programs hold raw addresses.

Real allocators (glibc's ptmalloc, jemalloc, mimalloc) use size classes: separate pools for small sizes so most requests are instant, plus per-thread caches, and they ask the OS for more memory with mmap when needed. Block headers that store sizes are left out here.

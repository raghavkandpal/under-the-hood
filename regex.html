Regex engines

A regular expression is a tiny program. Behind the scenes it's compiled into a state machine that reads text one character at a time. Build one, run it, and see the pattern that can freeze a web server.

Circles are states. Solid arrows consume a character, dashed ε-arrows are free jumps. Orange = every state the machine could be in right now. Blue ring = start, green ring = accept.

Catastrophic backtracking

Most popular engines (JavaScript, Python, Java, PCRE) don't track all states at once. They backtrack: try one way, and if it fails, rewind and try the next. Usually that's fine. But (a+)+b on a string of a's with no b has exponentially many ways to split the a's, and a backtracker tries them all before giving up.

What's going on

Thompson's construction (1968) turns each piece of a pattern into a small machine and plugs them together. A character is one arrow. A|B splits into both with ε-arrows. A* adds a loop back and a way to skip. The result has at most about twice as many states as the pattern has symbols.

Simulating every possibility at once. Instead of guessing which path to take, keep the set of all states you could be in and advance them together. Each character costs at most one pass over the states, so matching is linear in the text, with no blow-ups ever. Go's regexp, RE2 and Rust's regex crate work this way.

Why backtrackers exist anyway. Backreferences ((\w)\1) and some lookarounds can't be expressed as a finite state machine. Backtracking supports them, at the price of worst cases like the one above. Real outages have come from a single regex like this hitting an unlucky input ("ReDoS"). The usual defences are linear-time engines, time limits, or rewriting the pattern (a+b means the same as (a+)+b).

This engine supports literals, ., |, *, +, ?, parentheses and \-escapes, and matches the whole string. Its results are tested against JavaScript's built-in RegExp.

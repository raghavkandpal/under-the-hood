Exactly-once processing

A consumer reads 100 payments from a Kafka-style log and adds them up, then dies partway through. Whether the total comes out right depends on the order of two steps: saving its position and doing the work.

How it works

Where the position is saved. The consumer saves its offset (its position in the log) every 10 messages in this model. If it saves the offset first and then processes, a crash loses the unprocessed rest of the batch: at-most-once, between 0 and 9 messages missing. If it processes first and saves after, a crash replays everything since the last save: at-least-once, between 1 and 10 extra messages counted. Kafka's documentation describes both orders.

Try it: crash after message 25. Commit first has saved offset 30 and counts 95, five lost. Process first last saved 20 and counts 105, five twice. Transaction counts 100.

One transaction. Kafka can write the consumer's output and its new offset in a single transaction, so either both happen or neither does. A crash throws away the open batch and the restart redoes it, and the sink counts exactly 100 messages and the true total at every crash point.

Dropping duplicates. A sink that remembers each (partition, offset) it has applied can run at-least-once and still count exactly 100, because a replayed message has the same offset. Remembering the message content instead is wrong here: the log holds two identical payments on purpose, the second is a real payment, and the content check drops it. The sink comes up one short, 99.

The producer side. A producer whose acknowledgement is lost resends, and if the first copy had arrived the log now holds it twice. With 1 ack in 5 lost, this model's seeded run appends 23 extra copies and the log holds 123 messages. Kafka's idempotent producer attaches a producer ID and a sequence number to each message, and the broker drops any resend it has already appended: the log holds 100, with the same 23 resends.

The edge. Exactly-once covers what happens inside the pipeline. An email sent while processing is outside the transaction, so it goes out 100 plus the extra replayed messages, at the same crash points as at-least-once, even in transaction mode. The effect needs its own idempotency key, as in idempotency keys. Flink reaches the same result by taking consistent snapshots of its operators' state (Carbone et al.); that algorithm is not modelled here.

Simplified: one partition, one consumer, one crash and one restart, and the batch of 10 is this model's choice. Real Kafka transactions use a coordinator and fence old producers (see fencing tokens), which this page leaves out.

B-tree indexes

A table with a billion rows can find any one of them in a handful of disk reads. The trick is the B-tree, a short, wide search tree whose nodes are sized to fit a disk page. It's the default index in PostgreSQL, MySQL, SQLite and most file systems.

  • created by a split
Why "wide" wins: disk reads to find one row

How it works

A node is a sorted list of keys with a child pointer between each pair. To search, read the root, find which gap your key falls in, follow that pointer, and repeat. Each step reads one node, which on disk means one page.

Inserting always happens at a leaf. When a node overflows, it splits: the middle key moves up to the parent and the two halves become siblings. If that overfills the parent, it splits too. The tree only gets taller when the root splits, so every leaf is always at the same depth and the tree can't go lopsided. Insert keys in order and watch it stay balanced, where a plain binary search tree would turn into a long chain.

Why so wide? Reading from disk (even an SSD) costs far more than searching within a page you've already loaded. So real B-tree nodes hold hundreds of keys, one per 4–16 KB page. With 500 keys per node, three levels cover 125 million rows and four cover 62 billion. The top levels stay cached in memory, so a lookup often costs one or two actual reads.

Real databases usually use the B+tree variant: all values live in the leaves, which are linked left-to-right for fast range scans (WHERE price BETWEEN …), and inner nodes hold only separator keys. Deletion (merging and borrowing between siblings) is left out here.

What is an index?

To find one person in a long list, you can read every line, or jump to the right place because the list is sorted. A database index is a sorted copy that lets it jump.

One row among 1,000,000

How it works

The problem. A table is rows, like a spreadsheet of people with a last name and a first name. To find every Ortiz (in SQL, a WHERE clause says which rows you want), the database has no choice but a full scan: read every row and check it. The cost grows in step with the table. Databases store rows in fixed-size blocks called pages, and reading pages is the slow part.

The index. An index is a second, sorted copy of some columns, each entry pointing back to its row. Because it is sorted, the database can use binary search: look at the middle, discard the half that cannot hold the answer, repeat. A million sorted keys need at most 20 comparisons, since 220 is just over a million. Doubling the table adds at most one comparison.

On disk. Real indexes are stored as a B-tree: each page points to about 100 pages below it, so each step down the tree narrows the search 100-fold. For 1,000,000 rows at 100 rows per page, a scan reads 10,000 pages. The index walks 4 levels of tree (three levels hold at most 999,999 keys, one short of a million) and then fetches 1 table page: 5 pages, 2,000 times fewer.

Column order. This index is on (last name, first name): sorted by last name, and by first name within each last name, like a phone book. A search by last name jumps straight in, and last plus first narrows further. A search by first name alone can't jump in, because matching entries are scattered through the whole index, so this toy scans every row. Both SQLite and PostgreSQL sort this way: the leftmost column comes first.

Many matches. The search finds the first match, then reads along the sorted entries. A last name shared by dozens of people costs dozens of steps more than a full name that appears once. An index pays off when the answer is a small part of the table. When it is a large share, a scan can win, and query planners make that call.

The price. Every index is another structure to keep sorted. Inserting one row writes the table and each of its indexes: with 3 indexes, 4 structures. Indexes speed up reads at the cost of slower writes and more space, so add them for the queries you run, not for every column.

Try it. Look up a person by first name alone, then by last name. The full bar shrinks to a sliver.

Real planners may scan the whole index or skip-scan when the leading column is missing. The 2,000 names are made up.

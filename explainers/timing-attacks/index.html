Timing attacks

A server checks your API key with key === secret. That comparison stops at the first wrong character, so a key with the right first character is rejected a few nanoseconds later than one without. Measure carefully enough and the server tells you its secret, one character at a time.

How it works

The leak. An ordinary string comparison checks characters from the left and returns as soon as two differ. So its running time depends on how many leading characters of your guess are right. The difference is tiny, a few nanoseconds per character, but it's there on every request.

The attack. Try all 16 possible first characters, sending each many times and averaging the response times to cancel out network noise. The slowest one is probably right. Fix it, and repeat for the second character. Each position costs 16 × samples requests, so an 8-character hex key falls in 12,800 requests at 100 timings per guess, instead of the 4.3 billion that guessing whole keys would take. The last character is different: right or wrong, the comparison takes the same time, but there are only 16 candidates and one of them logs in.

Try it. Lower the timings per guess until the attack starts failing, then switch to the constant-time compare.

Noise only slows it down. Network jitter is far bigger than the leak, but it's random and the leak isn't, so averaging enough samples always wins: the noise shrinks with the square root of the sample count. Attacks like this have been shown across a local network and against cloud servers in the same data centre.

The fix. Compare secrets in constant time: look at every character whatever happens, and combine the differences so there's no early exit. Use the library function (crypto.timingSafeEqual in Node, hmac.compare_digest in Python) rather than writing your own, because compilers can turn a careful loop back into an early exit. Comparing hashes of the two values, or HMACs as JWT libraries should, also removes the signal. The same leak shows up wherever timing depends on secret data: password checks, crypto code, even cache behaviour.

Simplified: one comparison per character costs one time unit and noise is normally distributed. Real leaks are nanoseconds against milliseconds of jitter, so real attacks need thousands of samples per guess.

QUIC in depth

QUIC rebuilds TCP and TLS on top of UDP so a connection can start in fewer round trips, survive a change of network, and measure delay more cleanly. Each of those has a catch.

How it works

Fewer round trips. TCP finishes its handshake, then TLS 1.3 adds one more: two round trips before the request goes out, three before the first response byte arrives. QUIC carries the TLS handshake inside its own, so the request leaves after one round trip and the first byte arrives at two. A client that has talked to the server before can send the request in its very first packet ("0-RTT"), and the first byte arrives after one. These counts match the HTTP versions page, which also shows how QUIC stops one lost packet holding up other streams.

The amplification limit. UDP lets anyone forge a sender's address, so a server that answers freely could be used to flood a victim. Until the client's address is validated, a QUIC server may send at most three times the bytes it has received (RFC 9000 §8). The client pads its first packet to 1200 bytes, so the server's first flight is capped at 3600. A flight that fits finishes in one round trip. A longer one, such as a long certificate chain, is cut off, and the rest waits for the client's next packet to prove the address: one round trip more.

Try it. Move the flight from 3600 to 3700 bytes and watch the handshake take twice as long.

Migration. A TCP connection is named by its addresses and ports, so when a phone leaves Wi-Fi for mobile data the connection is gone, and the next request pays a new two-round-trip handshake before its own round trip. A QUIC connection is named by a connection ID that the new address can keep using, so the request goes out at once. The server still checks that the new address is real, with a PATH_CHALLENGE answered by a PATH_RESPONSE, one round trip that runs alongside the data (RFC 9000 §8.2, §9).

Cleaner delay samples. TCP retransmits a lost segment under the same sequence number, so an acknowledgement is ambiguous: it could answer the original or the copy. Karn's rule throws those samples away. QUIC gives every packet, retransmissions included, a new, ever-increasing packet number (RFC 9002 §4.2), so every acknowledged packet yields a sample. The more loss, the bigger the gap.

0-RTT replay. The data in a 0-RTT flight is sent before the server has proved it is live, so an attacker who captured it can send it again, and the server cannot tell the copies apart (RFC 9001 §9.2). A POST /pay replayed three times runs four times. Servers therefore accept 0-RTT only for requests that are safe to repeat, such as GET. A refused request is simply resent by the client once the handshake finishes, so it runs once.

Simplified: time is counted in whole round trips, the congestion window is ignored, and the server flight is a single number. Real packet loss and delay vary.

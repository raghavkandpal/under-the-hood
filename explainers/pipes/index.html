Shell pipes

cat huge.log | grep ERROR | head answers instantly even on a 10 GB file, using almost no memory. Each | connects two programs running at the same time through a small buffer. That buffer, and what happens when it's full or empty, is the whole trick.

How it works

All at once, not one after another. The shell starts every program in the pipeline at the same moment and connects each one's output to the next one's input with a pipe: a small buffer in the kernel, 64 KB on Linux. Lines flow through while cat is still reading. Nothing waits for a whole file to be written anywhere.

Backpressure. When a pipe fills up, the writer is simply paused by the OS until the reader catches up (indigo). When it's empty, the reader waits (blue). So the whole pipeline settles at the speed of its slowest program, and memory stays at a few buffers' worth, whether the file is a kilobyte or a terabyte. Try the slow sed pipeline and drag its speed.

Stopping early. head -n 10 exits after ten lines and closes its end of the pipe. The next time grep writes, the OS kills it with SIGPIPE, and the same happens to cat. Most of the file is never even read.

Some programs can't stream. sort can't output its first line until it has seen the last one, so it holds everything in memory (red count) and the stages after it sit idle. wc -l also reads everything, but only keeps a counter. Put grep before sort and it has far less to hold.

The same ideas appear in message queues, streaming frameworks and network flow control (TCP's window is backpressure too). Simplified: rates are fixed per program, and real pipes carry bytes, not lines.

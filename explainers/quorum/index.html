Quorum replication

Databases like Cassandra and DynamoDB keep every piece of data on several machines. They don't make every write wait for all of them. Instead they wait for W acknowledgements, and each read asks R replicas. Pick R and W well and you can't miss the latest write. Pick them badly and you get speed with stale answers.

How it works

The overlap rule. If R + W > N, any set of R replicas you read must include at least one of the W that took the latest write (there aren't enough replicas for the two groups to miss each other). The reader takes the highest version number it sees, so it always gets the newest value. With R + W ≤ N the groups can miss, and you sometimes read an old value. That's eventual consistency: it'll catch up, but not necessarily right now.

Latency. An operation finishes when the slowest of the replicas it waits for responds. Waiting for 1 replica means waiting for the fastest; waiting for all N means waiting for the slowest. That's why W = N or R = N hurts tail latency.

Availability. Crash replicas by clicking them. With N = 3 and R = W = 2, any one machine can fail and everything still works. Crash two and both reads and writes fail. W = 1 keeps accepting writes through more failures, but those writes live on fewer machines.

Common choices: N = 3 with R = W = 2 (balanced and consistent), W = N with R = 1 (fast reads, slow fragile writes), or R = W = 1 (fastest, eventually consistent), picked per query in Cassandra via its consistency levels.

Simplified: real systems also use read repair, hinted handoff and anti-entropy (often with Merkle trees) to bring stale replicas up to date in the background, and concurrent writes need version vectors or timestamps to resolve.

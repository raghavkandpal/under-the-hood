LZ77 compression

ZIP, gzip, PNG and HTTP compression all start with one trick: when something repeats, don't write it again. Write "go back d characters and copy n." Here it is working through your text, one decision at a time.

Examples:

The compressed stream
  • plain: literal
  • ⟵d,n: copy n chars from d back

How it works

Look back, then copy. At each position, search the recent past (the window) for the longest string that matches what comes next. If it's at least 3 characters, emit a back-reference (distance, length). Otherwise emit the character itself.

Copies can overlap themselves. "aaaaaaaa" becomes one a followed by "go back 1, copy 7". The copy reads characters it's writing as it goes, so long runs collapse to almost nothing. Try "One long run".

The window is a trade-off. A bigger window finds older repeats but costs more memory and search time, and needs more bits per distance. Set it to 8 characters and watch the repeats of "sea shells" go unnoticed. gzip uses 32 KB. Modern compressors like zstd and Brotli use megabytes.

Nothing compresses random data. With no repeats there's nothing to point back to, and the format's overhead makes it slightly bigger. That's why compressing an already-compressed file doesn't help.

Then Huffman. DEFLATE (the format inside ZIP, gzip and PNG) runs LZ77 first, then Huffman-codes the resulting literals, lengths and distances, so common ones get short codes. See the Huffman explainer for that half.

Size estimate: a literal costs about 9 bits (a flag plus 8 bits), a back-reference about 21 bits. Real formats are smarter, and greedy matching (always take the longest) isn't always optimal; zlib looks one step ahead ("lazy matching").

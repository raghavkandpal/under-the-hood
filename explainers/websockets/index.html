Polling vs WebSockets

HTTP only lets the browser ask. So how does a chat app show a new message the moment it's sent? Either ask over and over, ask and wait, or open a connection where the server can speak first.

  • event on the server
  • request
  • wait until delivered

How it works

Polling. The browser asks “anything new?” every few seconds. It's simple and works everywhere, but an event waits half the interval on average before anyone asks, and most requests come back empty. Each one carries several hundred bytes of HTTP headers, and the server has to handle every one of them from every user.

Long polling. The browser asks, and the server holds the request open until it has something to say (or a timeout, around 30 seconds, passes). Delivery is nearly instant. But every event costs a whole request and response, plus a round trip to set up the next one, so a busy stream ends up making more requests than plain polling would.

Try it. Push the events up to 60 a minute and compare the request counts for polling and long polling.

WebSockets. One HTTP request asks to upgrade the connection. After the server agrees, the same TCP connection carries small frames in both directions, each with a header of 2 to 14 bytes. Events arrive half a round trip after they happen, and an idle connection costs only an occasional ping. The price is a long-lived connection per user, which servers, load balancers and proxies all have to hold open.

Server-sent events. When only the server needs to push, as with notifications or live scores, SSE streams events down a normal HTTP response. With HTTP/2 many streams share one connection, and the browser reconnects by itself.

Simplified: header sizes are rough averages, the network never loses packets, and the server answers instantly. Real long polling also loses events that arrive while no request is open, unless the server queues them, as this one does.

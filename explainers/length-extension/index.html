Length extension attacks

A server that signs a message by hashing a secret followed by the message can be tricked into signing more. Someone who sees one valid signature can extend the message without ever learning the secret.

How it works

The weak signature. The server signs a query string by computing sha1(secret ‖ message), here a 16-byte secret and the 20-byte message user=alice&role=user. It accepts any message whose signature matches. The secret stays on the server, so nobody else should be able to make a valid one. See hash functions for what a hash is and JSON Web Tokens for a signature that is built correctly.

Padding. SHA-1 works on 64-byte blocks. Before the last block it appends a 0x80 byte, zeros, and the message length in bits as 8 bytes, so the total is a multiple of 64. A 55-byte message pads out to 64 bytes and a 56-byte one to 128, because the 0x80 byte and the length no longer fit in the first block. The 36 bytes of secret and message get 28 bytes of padding.

The hash is its own state. A SHA-1 digest is the five 32-bit words the computation holds after its last block. Anyone holding the digest of m can load those words, carry on at the byte count of m plus its padding, and hash more bytes x. The result equals sha1(m ‖ padding ‖ x), as if the hash had been run in one go.

The forgery. The attacker knows the message, its signature and the secret's length. They send the message, the padding that the server's hash would have added, and &role=admin, together with the signature they computed by resuming. The forged message is 59 bytes. The server hashes the secret and that message, gets the same value, and accepts it. Its parser takes the last role= it sees, so the role is now admin. The padding bytes look odd but nothing checks them.

Try it: set the guessed length to 15. The forged signature is the same as at 16, because the data still fills one 64-byte block, but the message carries one more padding byte and the server rejects it.

Not knowing the length. The attacker can just try 1, 2, 3 and so on, and ask the server each time. With the 16-byte secret the first success is at length 16, after 16 queries.

The fix. HMAC hashes twice with the key mixed in at both ends: sha1(key ⊕ opad ‖ sha1(key ⊕ ipad ‖ message)), as in one-time codes. The signature the attacker sees is the output of the outer hash, so it is not the state after the message, and resuming from it builds nothing the server accepts. Switch to HMAC-SHA1 and try all 64 lengths: every one fails. SHA-3 digests are not a resumable state, so it is not affected, but HMAC is the usual fix whichever hash you use.

Simplified: one message, one suffix, a secret that fits in one block, and a server that reads bytes as plain text. Real attacks on other hashes, such as SHA-256, use the same idea with different constants.

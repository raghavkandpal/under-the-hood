SIMD vectorisation

A processor can add eight numbers with the same instruction that adds one. Compilers use this automatically when they can prove it is safe, and the interesting part is when they can't.

  • differs

How it works

Lanes. A vector register is a wide box split into equal slots. A 128-bit register holds 4 float32, 2 float64 or 16 bytes. A 256-bit one holds 8 float32. One add instruction adds every slot at once, so the lane count is the register width divided by the element width.

A sum, in pieces. To add 1,003 float32 values on 8 lanes the loop runs 125 times, adding 8 values per step into 8 running totals. Three values are left over and are added one at a time. Finally the 8 totals are folded into one with 7 more adds. That is 135 instructions instead of 1,003, and more lanes shrink it further.

Try it. On Sum, compare floats with integers, then try a few seeds.

Why compilers ask permission for floats. Eight running totals add the values in a different order than left to right. Integer addition does not care about order, so the answer is identical. Float addition rounds after every step, so a different order gives a different last few digits. Compilers such as LLVM therefore vectorise float reductions only when told that reassociation is allowed, for example with -ffast-math.

Branches become masks. For if (x >= 128) sum += x the vector version compares all lanes at once, giving a mask of all ones or all zeros per lane. It ANDs the mask with the values and adds. Every lane does the same work whatever the data, so there is nothing to mispredict, and the cycle count is the same for sorted and random input. The scalar loop pays for each wrong guess, as in branch prediction.

Dependencies stop it. In c[i] = a[i] + b[i] every element is independent, so several at a time is safe. In a[i] = a[i-1] + b[i] each result needs the one just before it. Doing several at once reads old values for all but the first, which gives a different answer, so the compiler keeps the loop scalar. Compilers also add runtime checks that two arrays do not overlap before vectorising. Agner Fog's optimization guide and V8's WebAssembly SIMD post show the same ideas from the programmer's side.

Simplified: one cycle per instruction, three instructions per masked vector, and no memory costs. Real chips also have fused operations and several vector units.

Skip lists

A sorted linked list is simple, but finding something means walking it node by node. A skip list adds "express lanes": each node flips coins to decide how many lanes it joins. Searches zoom along the top lanes and drop down as they near the target, which is fast on average, with no rebalancing ever.

Bottom row = every key, in order. Each row above holds a random subset. The orange route is the last search: right while the next key is smaller, otherwise down.

How it works

Coin flips build the lanes. Every new key goes in the bottom list. Then flip a coin: heads, it also joins level 2. Heads again, level 3, and so on. With p = ½, about half the keys reach level 2, a quarter level 3, an eighth level 4. That's just like a balanced tree's levels, but arrived at by chance.

Searching. Start at the top-left. Move right while the next key is still smaller than your target. When it isn't, drop down a level. Each level roughly halves the remaining distance, so a search takes about log₂(n) steps on average. Compare the step count with the number of keys.

Why use one instead of a balanced tree? Inserting and deleting only touch a node's neighbours, with no rotations or rebalancing, which makes skip lists simple to write and friendly to concurrency (lock-free versions exist). Redis uses them for sorted sets, and LSM-tree storage engines use them for the in-memory memtable.

Guarantees are probabilistic: an unlucky run of coin flips could make a lane useless, but with many keys that becomes vanishingly unlikely. The p slider rebuilds the list. Higher p means more lanes and more memory.

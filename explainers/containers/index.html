Containers

“It works on my machine.” A container ships the machine too: your app, its exact libraries and its files, packed as a stack of read-only layers that run the same anywhere. Builds are fast because unchanged layers are reused, as long as you write the build steps in the right order.

How it works

Layers. Each instruction in a Dockerfile produces a layer: the files it added or changed. An image is the stack of them. A layer's ID is a hash of its parent's ID, the instruction, and the contents of any files it copies, so if anything above it changes, so does it.

The cache. On rebuild, Docker walks down the steps and reuses each layer whose ID it already has. At the first miss it stops, and every step below runs again. In the “copy everything first” order, editing one line of server.js changes the COPY . . layer and forces a 45-second npm ci. Copy only the dependency files first, install, then copy your code, and everyday edits skip the install entirely: 13 seconds instead of 58, most of it your own build step. Edit package.json and the install reruns, as it should.

Shared on disk. Ten services built FROM the same base image store that base once, and pulling an update downloads only the layers that changed.

Not a virtual machine. A container is an ordinary process on the host's kernel, wearing blinkers. Namespaces give it its own view of process IDs (it thinks it's PID 1), the filesystem (the image), network and hostname. Cgroups cap its CPU and memory: go over the memory limit and the kernel kills it (“OOMKilled”). It starts in milliseconds and adds almost no overhead, but it shares the host kernel, so it's a weaker security boundary than a VM.

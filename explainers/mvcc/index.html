Multi-version concurrency control

In most databases, a long report and a stream of updates can run on the same table at once, and neither waits for the other. The trick is that an update never overwrites a row. It writes a new version, and each transaction reads the versions that existed when it began.

Row versions

How it works

Versions, not overwrites. Every version of a row is stamped with the transaction that created it and, once it's replaced or deleted, the transaction that did that. PostgreSQL calls these xmin and xmax. An update writes a new version and sets the old one's xmax; the old version stays on disk for anyone who still needs it.

Snapshots. When a transaction begins, it notes which transactions have committed so far. A version is visible to it if its creator is in that list (or is itself) and its replacer isn't. That single rule gives each transaction a frozen picture of the database: changes committed later, or still in progress, are invisible to it. Readers never take locks, so they never block writers, and writers never block readers.

Try it. Begin both, have A write and commit, and read in B. Begin a fresh transaction to see the new value. Then try writing in both.

Write conflicts. If two transactions both change the same row, the second one finds that the version it can see has already been replaced by someone else. Under snapshot isolation, it must abort and retry; otherwise one update would silently overwrite the other (the lost update from isolation levels). PostgreSQL reports this as “could not serialize access due to concurrent update”.

Aborts are free, cleanup isn't. Aborting just marks the transaction aborted: its versions become invisible and nothing needs undoing. But replaced versions pile up. Vacuum removes the ones no running transaction can still see. A transaction left open for hours keeps every version since it began alive, which is how one forgotten session can bloat a busy table.

Simplified: one row, one value, and only write-write conflicts are checked. Real snapshots are a range of transaction ids rather than a list, and full serializable isolation also tracks reads.

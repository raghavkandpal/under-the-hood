Dynamic programming

Make 6p from coins worth 1, 3 and 4. Grabbing the biggest coin each time gives 4 + 1 + 1, three coins, but 3 + 3 does it in two. Finding the true best seems to mean trying every combination, and there are astronomically many. Dynamic programming finds it by never solving the same small problem twice.

Each cell: amount (small), fewest coins to make it (bold), and the last coin used. Hover a cell to see which smaller answers it was built from.

How it works

Break it into smaller versions of itself. The best way to make 6 ends with some coin. If it's a 3, the rest is the best way to make 3, and if it's a 4, the best way to make 2. So best(6) = 1 + min(best(5), best(3), best(2)). Each answer is built from answers to smaller amounts.

Overlapping subproblems. Written as plain recursion, best(6) asks for best(5), which asks for best(4)… and best(3) gets recomputed again and again along different branches. The work explodes exponentially (see the call counts). Remember each answer the first time (memoisation), or fill a table from 0 upwards as here, and every subproblem is solved exactly once.

Greedy isn't always wrong. For everyday coin systems, taking the biggest coin is optimal, and currencies are designed that way. Pick the 1, 3, 4 or 1, 7, 10 systems and press “Find where greedy loses”.

The same pattern solves edit distance (spell checkers, diff), shortest paths (Bellman-Ford, as in routing), sequence alignment in genomics, the knapsack problem, speech recognition (Viterbi), and how a typesetter breaks a paragraph into lines.

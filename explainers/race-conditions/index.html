Race conditions & locks

Two threads each add 1 to a shared counter. It starts at 0, so it should end at 2. Sometimes it ends at 1. You're the operating system here: you choose which thread runs next, one instruction at a time.

What's going on

count++ is three steps. Load the value into a register, add 1, store it back. If thread 2 loads before thread 1 stores, both read 0, both write 1, and one increment vanishes: a lost update. Of the 20 possible orderings, only 2 are correct: the ones where one thread finishes completely before the other starts. Real threads switch at unpredictable moments, so the bug shows up rarely, randomly, and usually not on the developer's machine.

A lock (mutex) makes the three steps atomic as far as other threads can tell. Only one thread can hold it, and the other blocks (red) until it's released. Switch to "count++ inside a lock": every interleaving now gives 2.

Locks bring their own trap: deadlock. Thread 1 takes A then wants B. Thread 2 takes B then wants A. If each grabs its first lock before the other's second, they wait forever. The cure is to always acquire locks in the same global order, so a cycle can't form. Compare "two locks, opposite order" with "same order".

Real CPUs make this harder still: caches and compiler reordering mean threads can even see each other's writes out of order without proper synchronisation. That's what memory models and atomic instructions are about.

LSM trees

A B-tree updates data in place, so every write is a small, scattered disk write. Databases built for heavy write loads (RocksDB, Cassandra, LevelDB, ScyllaDB) do something else: never overwrite anything. Buffer writes in memory, dump them as sorted files, and tidy up later.

How it works

Writes are cheap. A write goes into an in-memory sorted memtable (plus an append-only log for crash safety). When the memtable fills, it's written to disk in one sequential burst as a sorted, never-modified file, an SSTable. Sequential writes are what disks and SSDs do fastest.

Updates and deletes are just newer writes. Overwriting "cat" doesn't touch the old file. A newer entry simply shadows it. A delete writes a tombstone (red) saying "this key is gone".

Reads pay instead. A read checks the memtable, then each SSTable from newest to oldest, until it finds the key (blue outline = checked, green = found). The more tables pile up, the slower reads get. Real systems keep a Bloom filter per table to skip most of them.

Compaction cleans up. In the background, tables are merge-sorted into fewer, bigger ones: newest version wins, shadowed versions and tombstones disappear. It keeps reads fast and reclaims space, but rewrites data repeatedly. That's write amplification, the price of cheap writes. It starts below 1 here, because repeated keys collapse in the memtable and the latest writes haven't reached disk yet. Keep adding data and it climbs past 1 as compaction rewrites the same rows again and again. Real engines commonly see 10× or more.

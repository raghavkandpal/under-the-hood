SQL joins

A join stitches two tables together on a shared column, such as customers and their orders. The kind of join decides what happens to rows with no partner, and the algorithm the database picks decides whether it takes milliseconds or hours.

How the database actually does it

How it works

Inner join keeps only pairs that match. A customer with no orders disappears, and so does an order whose customer doesn't exist. Left join keeps every customer and fills in NULL where there's no order, which is how you find "customers who never ordered" (WHERE o.id IS NULL). Right is the mirror image. Full outer keeps everything from both sides. Cross join pairs every row with every row: 3 × 4 = 12 rows here, a trillion with two million-row tables. An inner join that forgets its ON clause becomes one.

One-to-many multiplies rows. A customer with two orders appears twice in the result. That's how a careless join makes SUM() double-count.

NULL never equals anything, not even another NULL, so rows with a missing key never match.

Three algorithms

Nested loop compares every customer with every order, n × m steps. It's fine for tiny tables, or when an index lets it look up each match directly instead of scanning. Hash join loads the smaller table into a hash table, then streams the bigger one past it, n + m steps, but it needs memory for the hash table. Sort-merge join sorts both sides and walks them together like a zipper. Sorting costs n log n, unless an index already keeps them sorted, and then the join is nearly free.

The query planner chooses using statistics about table sizes. Run EXPLAIN on a slow query and you'll see which one it picked, often a nested loop that assumed a table was small.

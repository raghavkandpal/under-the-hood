Two's complement

Inside a CPU there are no minus signs, only bits. So how are negative numbers stored, and why does adding 1 to the biggest number suddenly give the most negative one? The answer is an elegant trick that lets the same adder circuit handle positive and negative numbers alike.

The 8-bit number wheel

How it works

The top bit counts as negative. In 8 bits, the leftmost bit is worth −128 instead of +128, and the rest are worth 64, 32 … 1 as usual. So 11111111 is −128 + 127 = −1, and 10000000 is −128. The range is −128 to 127.

Negating: flip every bit, then add 1. 5 is 00000101. Flip it to get 11111010, add 1 for 11111011, which reads as −5. Press "a = −a" to watch. There's one odd case: −128 has no positive partner, so negating it gives −128 again.

Why bother? Because ordinary binary addition, carries and all, now just works for negative numbers too: 5 + (−3) adds the bit patterns and drops the final carry to give 2. The CPU needs one adder, not separate add and subtract logic, and comparisons stay simple.

Overflow. The patterns wrap around like a clock (see the wheel). 127 + 1 lands on −128. CPUs set two flags: carry (the result didn't fit as an unsigned number) and overflow (it didn't fit as a signed one). Languages differ on what happens next: C has undefined behaviour for signed overflow, Rust panics in debug builds, Java silently wraps. Famous bugs, from game scores flipping negative to Ariane 5's self-destruct in 1996, came from numbers outgrowing their bits.

Shown at 8 bits so everything fits. Real CPUs use the same scheme at 32 or 64 bits.

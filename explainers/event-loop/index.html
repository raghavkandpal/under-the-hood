The event loop

JavaScript runs your code on a single thread, yet a web page juggles clicks, timers and network replies without freezing. The trick is a loop that runs one piece of work at a time, plus a few queues of what to do next. It also explains why setTimeout(fn, 0) isn't immediate and why a promise callback beats it.

How it works

  
One thing at a time. The call stack holds whatever function is running now. JavaScript never interrupts it: a click, a finished timer or a network reply has to wait until the stack is empty. That's why a long loop freezes the page. Try “A timer can't interrupt busy code”.

  
Timers live outside. setTimeout hands the waiting to the browser (or Node) and returns at once. When the time is up, the callback joins the task queue. It runs only when the stack is empty and it reaches the front. The delay is a minimum, never a promise.

  
Microtasks cut in line. Promise callbacks (.then, and the code after await) go into a separate microtask queue, which is completely drained after every task, before the next task or the next screen repaint. That's why “3” prints before “2” in the classic puzzle, even with a 0 ms timer. Microtasks that queue more microtasks run straight away too, so an endless chain of them can starve timers and rendering just like a busy loop.

  
The loop: run one task to completion, drain all microtasks, maybe repaint the screen, take the next task, and so on. Node.js has the same core with a few extra phases for I/O.

  
Real browsers have several task queues (input often gets priority), clamp nested timers to ≥ 4 ms, and repaint about every 16 ms when there's time. Web Workers give you extra threads, each with its own loop. Related: race conditions, which are what you get with real threads instead.

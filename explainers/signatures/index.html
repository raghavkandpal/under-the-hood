Digital signatures

How does your computer know a software update really came from its maker, or that a website's certificate is genuine? With a signature only one key can make but anyone can check. Here's RSA, small enough to watch.

Alice (signer)

Bob (verifier)

He has the public key (n, e), the message he received, and the signature.

Mallory (forger)

She wants Bob to accept “Release v2.4.1-evil is safe to install.”

How it works

Two keys. Alice picks two secret primes p and q and publishes their product n with an exponent e. From p and q she can compute a private exponent d that undoes e: (xᵈ)ᵉ ≡ x (mod n). Without the factors, nobody knows how to find d.

Signing means hashing the message to a number h and computing s = hᵈ mod n, which only the holder of d can do. Verifying means computing sᵉ mod n with the public key and checking that it equals the hash of the message received. Change one character and the hash changes completely, so the check fails.

Why forging fails. Guessing is hopeless: there are n possible signatures and exactly one works. The only known shortcut is factoring n, which is easy here and infeasible at real sizes. RSA keys are 2048–4096 bits, about 617–1234 decimal digits, and no known method factors them in any reasonable time.

Where this shows up. Software updates and app stores check the vendor's signature. HTTPS certificates are a chain of signatures: a certificate authority signs "this public key belongs to example.com", and your browser ships with the authorities' public keys. That's the missing piece from the key exchange explainer, and it's how you know you're not talking to Mallory.

Toy version: textbook RSA with a truncated SHA-1 hash. Real systems use padding schemes (RSA-PSS), modern hashes, and increasingly elliptic-curve signatures (Ed25519, ECDSA), which are much smaller for the same security. Don't use this code for anything real.

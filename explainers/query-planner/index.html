Query planners & indexes

You don't tell a database how to find your rows, only which rows you want. A planner guesses how many rows will match and picks a strategy. Guess right and the query takes milliseconds. Guess wrong and the same query takes minutes, with nothing in your code changed.

SELECT * FROM products WHERE price < ;

    

    
    

  


  
How it works

  
Two ways to answer. A sequential scan reads the whole table, page after page, which is cheap per page because disks and caches love reading in order. An index scan walks a B-tree straight to the matching prices, then fetches each row from wherever it lives in the table, often a random page every time. For a handful of rows the index wins enormously. Past a surprisingly small fraction of the table, all those random reads cost more than just reading everything.

  
The crossover is around half a percent of rows on a spinning disk here. On an SSD random reads are nearly as cheap as sequential ones, so the index stays worth it for longer. If the table is physically stored in price order (clustered), matching rows sit next to each other and the index wins almost everywhere.

  
Estimates come from statistics. The planner can't count matches without running the query, so it keeps a histogram per column: bucket boundaries that each hold the same number of rows. “Price < 5” falls in the first bucket, so it estimates a share of that. Statistics are refreshed periodically (ANALYZE), but data can change faster. Tick “stale” and lower the threshold to about 5: the planner expects almost nothing to match, picks the index, then fetches tens of thousands of rows one random read at a time.

  
Real planners also weigh joins (nested loop, hash, merge), sort order, caching and multi-column indexes, where column order decides which queries can use them. EXPLAIN ANALYZE shows estimated vs actual rows; a big gap is the first thing to look for. Costs use Postgres's default units. Table: 1,000,000 rows, 100 per page.

Register allocation

A CPU has a handful of registers, the only places it can do arithmetic, and programs have far more variables. The compiler decides which variable lives in which register, line by line. When it runs out, it spills a variable to slow memory. Underneath it's a puzzle you may know: colouring a map so that no neighbours match.

How it works

Liveness. A variable is live from where it's assigned to its last use. After that its register is free for someone else. The bars show each variable's live range, line by line.

Interference. Two variables alive at the same moment can't share a register. Draw each variable as a dot and join every pair that's alive together. Giving each register a colour, the job becomes: colour the dots so no two joined dots match, using at most k colours. That's graph colouring.

Hard in general, easy here. Finding the fewest colours for an arbitrary graph is NP-hard. Live ranges in straight-line code are intervals, though, and for intervals a greedy sweep in start order, which is linear scan allocation, is provably optimal: it needs exactly as many registers as the most variables alive at once. JIT compilers such as V8 and HotSpot use linear scan because it's fast. Ahead-of-time compilers such as GCC and LLVM spend longer on smarter colouring, because loops and branches make the graph messier.

Spilling. With too few registers some variables get stored to the stack and reloaded when needed (striped). Each spill costs memory traffic, so compilers prefer to spill variables that are used rarely or outside hot loops. Drag the register count down to 1 and watch.

Real allocators also coalesce copies (x = y can reuse y's register), respect registers that a call or instruction clobbers, and can split a long live range so only part of it spills. x86-64 has 16 general-purpose registers. ARM64 has 31.

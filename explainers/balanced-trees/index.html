Balanced search trees

A binary search tree finds any key in a few steps, as long as it stays bushy. Feed it keys in sorted order and it grows into a long chain. AVL trees fix that with small local rotations.

How it works

Search trees. Every node's left subtree holds smaller keys and its right subtree larger ones, so a search goes left or right at each node and never backtracks. The cost is the depth of the key. A tree of 31 keys can be 5 levels deep, or 31.

The bad case. Insert keys in sorted order and each one is larger than everything so far, so it goes to the far right. The tree becomes a linked list and search is O(n). Sorted input is common in real life: ids, timestamps, names loaded from a sorted file.

Rotations. A rotation turns a parent and child around: the child moves up, the parent moves down to the other side, and one subtree changes hands. In-order is preserved, so the tree still sorts correctly, and only three pointers change. An AVL tree records each node's height. After an insert, it walks back up, and wherever one side is two levels taller than the other it rotates once, or twice when the new key went in on the inside (the LR and RL cases).

Try it. Insert the sorted keys one at a time in AVL mode and watch where each rotation happens. Then insert them all without balancing.

What it guarantees. No AVL tree is ever more than about 1.44 log₂ n deep, so search, insert and delete are O(log n) whatever order keys arrive in. Red-black trees, used by Java's TreeMap and Linux's scheduler, loosen the rule to rotate less often. Databases use the same idea with hundreds of keys per node: the B-tree.

Simplified: insert only, with distinct integer keys. Deletes rebalance the same way but can rotate at every level on the way up.

Serving 10,000 connections

A chat server holds thousands of connections that are almost always silent. How it waits for the few that speak decides whether it needs one core or a hundred: one thread per connection, one loop asking every connection, or one loop the kernel tells.

  • poll loop
  • epoll loop

How it works

A thread each. The simplest server gives every connection its own thread, which blocks in read() until data arrives. The code is straightforward, and CPU use is fine. The cost is memory: each thread needs a stack and kernel bookkeeping, tens of kilobytes even when idle, so 10,000 connections hold most of a gigabyte. Every request also costs two context switches, and at a hundred thousand threads those alone eat the machine.

One loop with poll. Instead, one thread can ask the kernel “which of these connections have data?” with select() or poll(), then handle just those. Memory per connection drops to a buffer. But every call passes the whole list in, and the kernel checks every descriptor, ready or not. With 10,000 mostly idle connections, almost all the CPU goes on asking. Under load the loop handles many ready connections per call, which stretches each pass to over a millisecond, but it still can't keep up with more.

Try it. Hold the requests at one a second and slide the connections from 100 to 100,000. Find where each line hits the top.

One loop with epoll. Linux's epoll (kqueue on BSD and macOS, IOCP on Windows) turns it around. You register each connection once, and the kernel keeps a list of the ones that became ready. Each epoll_wait() returns only those, so the cost tracks the traffic, not the number of idle connections. That's what let a single server hold 10,000 connections around 2000 (the “C10k problem”), and millions today. Node.js, nginx and Redis are all built on such a loop; see the event loop.

Simplified: a cost model, not a benchmark. The constants (20 µs a request, 3 µs a context switch, 0.1 µs per descriptor checked, 80 KB a thread) are rough, and real servers add worker threads to use more than one core.

HyperLogLog

How many different people visited today? Keeping every id you've seen takes memory in proportion to the answer. HyperLogLog gets within a few percent of a billion using about a kilobyte, by watching for unusually lucky hashes.

100,000 visitors, 20 trials each

How it works

Lucky runs. Flip a coin until it lands heads. A run of 10 tails before the first heads happens about once in 1,024 tries. So if someone tells you the longest run they saw was 10, they probably tried around a thousand times. Hash every visitor id into random-looking bits and count the leading zeros: the longest run you've seen tells you roughly how many distinct ids there were. Repeats hash the same way, so seeing a visitor twice changes nothing.

Averaging. One longest run is a wild guess, off by a factor of two either way. So HyperLogLog splits the hashes into m buckets (the first few bits pick the register) and keeps the longest run per register. Combining them with a harmonic mean, which isn't thrown off by one lucky register, and a correction constant gives an estimate with a standard error of about 1.04/√m: 3% with 1,024 registers, under 1% with 16,384.

Tiny memory. A register only needs to store a number up to about 64, which is 6 bits. 16,384 registers are 12 KB, and that sketch counts up to billions of distinct items at under 1% error. Redis's PFCOUNT works exactly like this.

Try it. Push the visitors to a million and the registers down to 16, then up to 16,384, and compare the error with the table.

Merging. Two sketches of the same size combine by taking the larger value in each register. The result is exactly the sketch you'd have built from both streams, so servers can count separately and merge, and daily sketches combine into a weekly unique count without double-counting anyone.

Simplified: 32-bit hashes and only the small-range correction. Production versions use 64-bit hashes, a sparse format while the count is small, and bias tables (HyperLogLog++).

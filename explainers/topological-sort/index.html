Topological sort

A build has steps that depend on other steps. Any order works as long as nothing runs before what it needs. Finding one is a topological sort, and the same algorithm notices when the dependencies go round in a circle.

    How it works

    The graph. Draw each task as a node and an arrow from every task to each one that needs it. Without circles, that's a directed acyclic graph, or DAG. A topological order lists the nodes so that every arrow points forwards. Build tools, spreadsheets recalculating cells, package installers, course prerequisites and make all need one.

    Kahn's algorithm. Count each task's unmet dependencies, the small number on each box. Tasks with zero are ready. Take any ready task, put it next in the order, and cross it off: every task that needed it now has one fewer unmet dependency, and any that hit zero become ready. Repeat until nothing is ready. Each arrow is crossed off once, so it runs in O(nodes + arrows).

    Many right answers. When several tasks are ready at once, any of them can go next. This build has 48 valid orders. Tasks that are ready together don't depend on each other, so a build tool can run them in parallel, which is how make -j keeps every core busy.

    Try it. Tick the extra arrow so deploy must happen before codegen, and run to the end.

    Cycles. If tasks depend on each other in a circle, none of them ever reaches zero. The algorithm stops with tasks left over, and those leftovers are exactly the ones in the cycle or waiting behind it. That's how a package manager reports a circular dependency instead of hanging.

    Simplified: ties are broken by list order. Depth-first search gives another classic algorithm: list each task after everything below it is finished, then reverse the list.

Type inference

You never wrote a type, yet the compiler knows fun x -> x works on anything. It gives every unknown a variable, collects equations between them, and solves the equations.

Constraints

    Bindings

      How it works

      Constraints. Inference walks the program and gives each unknown its own type variable, written t1, t2… while it works. In this model, + takes two integers. So fun x -> x + 1 gives x the variable t1 and produces 2 constraints, t1 = int and int = int. Solving them binds t1 to int, and the type is int -> int.

      Unification. Solving a constraint makes both sides equal by binding variables, taking a function type apart into its argument and result. For fun f -> fun g -> fun x -> f (g x) the 2 constraints come from the 2 applications, and the answer is ('a -> 'b) -> ('c -> 'a) -> 'c -> 'b. Finished types are renamed 'a, 'b… in order of first appearance, so the same shape always prints the same way. When two sides can't be made equal, as in if true then 1 else false, the branches must agree and inference stops: cannot unify int with bool.

      The occurs check. In fun x -> x x, x is used as a function of itself. The one constraint says 'a would have to equal 'a -> 'b, a type that contains itself and never ends. The occurs check refuses that binding. Turn it off and the solver binds t1 := t1 -> t2 and stops there, because applying that binding again and again would never finish.

      Let-polymorphism. A let solves its own constraints first, then turns the variables nothing outside refers to into "any type", so each use of the name gets fresh variables. That is why let id = fun x -> x in let a = id 0 in id true is bool: id is used at int and at bool. A function parameter gets no such treatment. In (fun id -> let a = id 0 in id true) (fun x -> x) the parameter id has one type, and it can't be both int -> t and bool -> t: cannot unify int with bool.

      Order. The orders agree tile re-solves the same constraints in 20 seeded shuffles and counts how many give the same outcome as the generated order: a type, the same one, or a failure. A failure counts as agreeing even when the message differs. Shuffling happens inside one scope, because a let solves its own constraints before the outer ones. Only 4 of the 8 tabs have 2 or more constraints in a scope: compose, add one, bad if and parameter. For those, all 20 agree and the slider changes the lists while the type stays. For the others the tile reads n/a and the slider changes nothing.

      Limits. Programs are capped at 300 characters, and inference stops with a message when a type passes 200 parts, because types can double in size with every let.

      Try it: pick self-apply, then turn the occurs check off. Edit the program to fun x -> x + x and it types again.

      A toy: integers, booleans, +, if, fun, application and let, with no recursion, no mutable references, no records and no friendly error messages. Real languages add more rules on top of this core.

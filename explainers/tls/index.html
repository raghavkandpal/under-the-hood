The TLS handshake

Every https:// page starts with a few messages that, within a round trip, agree on a secret key with a server you've never met and prove that server really is who it claims. It's key exchange and digital signatures working together.

After the handshake: send something private

What each step is for

ClientHello / ServerHello: agree on a key. Each side sends a random number and a Diffie-Hellman key share. From A and B, both compute the same secret, and an eavesdropper who sees A and B can't. In TLS 1.3 this all happens in the first round trip.

Certificate: who are you? The server sends a certificate: "the public key for bank.example is n, e", signed by a certificate authority. Your browser ships with the CAs' public keys, so it can check that signature. A self-signed or forged certificate fails here.

Checks: right name, still valid. A perfectly genuine certificate for a different site is useless to an attacker, because the browser checks the name. Expired certificates are rejected too.

CertificateVerify: prove you own it. Certificates are public, so anyone can replay the bank's. The server therefore signs the handshake transcript with the certificate's private key, which an impostor doesn't have. This also ties the key exchange to the identity, so Mallory can't splice her own DH share into a genuine-looking session.

Finished: nothing was tampered with. Each side sends a MAC of the whole conversation under the new key. If anyone altered a single byte on the way, the MACs won't match.

Toy version of TLS 1.3's shape: real TLS uses elliptic-curve DH (X25519), RSA-PSS or ECDSA signatures, HKDF key derivation, AES-GCM or ChaCha20-Poly1305 encryption, and certificate chains with intermediates. The numbers here are tiny so you can read them. Never use this for real security.

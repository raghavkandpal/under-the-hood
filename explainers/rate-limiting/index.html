Rate limiting

Every public API caps how fast you can call it, to protect itself from overload, abuse and runaway scripts. "100 requests per minute" sounds simple. Three common ways to enforce it behave quite differently when traffic gets lumpy.

Three algorithms

Fixed window. Count requests per calendar second (or minute), and reset at the boundary. It's dead simple, a single counter. Its flaw: a client can send a full allowance just before the boundary and another just after. Pick "Burst at a window boundary" and the busiest real second sees about twice the limit.

Sliding window. Remember the timestamp of every accepted request and allow a new one only if fewer than limit fall in the last second. It's exact: no second ever exceeds the limit. The cost is memory per client. Production systems often approximate it by blending the current and previous fixed windows.

Token bucket. A bucket holds up to limit tokens and refills at limit per second, and each request spends one. Bursts are allowed up to the bucket size, then traffic is held to the refill rate (the orange line shows the tokens). It needs only two numbers per client, and it's what AWS, Stripe-style APIs and Linux traffic shaping commonly use. Capacity and refill rate can also be set separately, say "bursts of 50, sustained 10/s". Note that its busiest second can exceed the limit too, by up to a full bucket plus one second of refill. That's deliberate: a token bucket caps the burst size and the long-run rate, not every one-second window. If you need a hard per-second ceiling, use a sliding window.

Clients should back off when they get HTTP 429 (Too Many Requests), ideally honouring the Retry-After header and adding random jitter so they don't all retry at once.

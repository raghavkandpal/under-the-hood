CPU caches & locality

The same loop over the same data can run several times slower depending only on the order you visit it in. The reason is the cache, a tiny, fast memory that only pays off if you use what it just fetched.

Why order matters

Memory arrives in lines. When the CPU misses, it doesn't fetch one int. It fetches a whole cache line of neighbours, 64 bytes on real chips, betting you'll want them next. This is spatial locality. Walking row by row uses all of each line, so you get one miss and then several hits.

Columns waste it. In a row-major matrix, going down a column jumps a whole row each step. Each access lands on a different line, and by the time you come back for the neighbours the line has been evicted to make room. Almost every access misses.

Tiling fixes it. Work in small blocks that fit in the cache, and the neighbours are still there when you need them. Fast matrix multiplication, image processing and database joins all use this trick.

Associativity. Each line can only live in one set, picked by its address. Direct-mapped caches give each set a single slot, so two hot addresses that share a set keep evicting each other. More ways mean fewer of these conflict misses, at the cost of more hardware.

Sampling profilers

Where does a program spend its time? Instead of timing every function call, a sampling profiler interrupts the program at random moments and writes down what it was doing. Add up enough snapshots and the slow parts stand out.

How it works

Sampling. Many times a second (often 100 to 1,000), a timer interrupts the program and the profiler records the call stack: the function running now, the one that called it, and so on up to main. It never touches the program's code, so it slows it down by a percent or two. A function that runs 35% of the time shows up in about 35% of the samples. With n samples the error shrinks like 1/√n: a hundred samples give a rough picture, ten thousand an accurate one.

Flame graphs. Merge identical stacks and draw them as boxes: the root at the top, each function below the function that called it, as wide as its share of samples. A box's width counts time in that function and everything it called; the part not covered by boxes below it is its own (self) time. Wide boxes with nothing underneath are where the CPU is actually busy.

Try it. Find the hottest function in the table, then find it in the flame graph. It appears twice, and neither box looks like the biggest.

Two views. The flame graph splits a function by who called it. That's what you want for “which feature is slow?”, but a utility called from many places, like a JSON parser, gets sliced into narrow boxes and looks harmless. A table of self time per function adds the slices back together. Real profilers (perf, pprof, Chrome DevTools, py-spy) offer both, plus an inverted flame graph that starts from the busy functions and shows their callers.

Instrumenting instead. The alternative is to add timing code to every function entry and exit. That gives exact call counts, but the timing code itself costs time, which distorts small, frequently called functions most: exactly the ones you're looking for.

Simplified: a fixed made-up program, each function's self time in one block, and perfectly random sample times. Real samplers can be biased toward points where the program can safely be interrupted (safepoints).

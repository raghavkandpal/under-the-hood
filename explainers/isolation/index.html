Transaction isolation

Databases run many transactions at once, but each is supposed to act as if it had the database to itself. How strictly that's enforced is the isolation level. Each step up blocks another kind of bug, and costs a little more. Pick a bug and a level, then watch two transactions collide.

The four anomalies

Dirty read: seeing another transaction's uncommitted change, which may be rolled back. Almost every real database prevents this by default.

Non-repeatable read: reading the same row twice in one transaction and getting different answers, because someone committed in between. A report that adds up figures can contradict itself.

Lost update: two read-modify-write cycles overlap and the second write silently overwrites the first. It's the database version of the race condition.

Write skew: two transactions each read the same facts, each check a rule, and each change a different row. Neither conflicts with the other directly, yet together they break the rule. Snapshot isolation misses this. Only true serializability catches it.

How the levels work

Read committed (PostgreSQL's default) reads the latest committed value at each statement. Snapshot isolation (PostgreSQL's "repeatable read") gives each transaction a frozen snapshot from its start and aborts the second of two transactions that write the same row. Serializable additionally aborts a transaction if something it read was changed underneath it, so the result always matches some one-at-a-time order.

Prevention means aborting. At the stricter levels the database doesn't magically merge conflicting work. It refuses one transaction with a serialization error, and your application has to retry it. That's the cost of correctness, and the reason defaults are usually weaker.

Simplified multi-version model in the style of PostgreSQL: snapshot from transaction start, first-committer-wins on write conflicts, and serializability by validating the read set at commit (real SSI tracks dependencies more precisely and aborts less often). Other databases differ: MySQL's default is "repeatable read" with locking reads, SQL Server uses locks unless snapshot is enabled.

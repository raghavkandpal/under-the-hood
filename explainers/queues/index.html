Queues & Little's law

Why does a server at 90% CPU feel slow when 70% felt fine? Why do airports use one long snaking line instead of a line per desk? Queueing theory answers both. The answers are counter-intuitive, and they apply to every system that serves requests.

Three results worth knowing

1. Utilisation is a trap. For one server with random arrivals, the average time in the system is 1 / (μ − λ). At 50% busy, a request spends about 2× its service time in the system. At 90% it's 10×, and at 99% it's 100×. Push the arrival slider toward the limit and watch the curve go vertical. That's why systems are run with headroom, and why "the database is only at 85%" is not reassuring.

2. Little's law: L = λ × W. The average number of things in a system equals the arrival rate times the average time each spends there. It holds for almost any stable system: queues, warehouses, open bug tickets, requests in flight. If 10 requests arrive per second and each takes 0.3 s, about 3 are in progress at any moment. The "L vs λW" stat checks it live.

3. Pool your queues. With three servers and three separate lines, one line can be stuck behind a slow customer while another server sits idle. One shared line never wastes a free server. Untick "one shared line" at the same load and the wait jumps several times over. It's the same reason a thread pool with one work queue beats pinning tasks to threads.

Arrivals are random (Poisson) and service times are exponential, the classic M/M/c model. Theory uses the Erlang C formula. Each run simulates 20,000 customers and discards the first 10% as warm-up.

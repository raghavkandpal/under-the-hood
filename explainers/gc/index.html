Garbage collection

In Python, Java, JavaScript or Go you create objects and never free them. Something has to work out which ones you're finished with. Here are the two classic answers, and the case where one of them fails.

Two ways to find garbage

An object is garbage when nothing your program can still reach points to it, directly or through other objects. The roots (local variables, globals, the call stack) are where every search starts.

Reference counting keeps a count on each object of how many references point at it (the small number). When the count hits 0, the object is freed at once, and its own references are released, which can cascade. It's simple and immediate, with no pauses. But in a cycle each object keeps the other's count at 1 forever, even when nothing else can reach them. Load "a cycle", switch to reference counting, and clear y. The two objects turn red: leaked.

Mark & sweep ignores counts. From the roots it follows every reference and marks what it reaches (green), then sweeps away everything unmarked. Cycles are no problem. The cost is that it has to run every so often, and naive versions pause the program while they do.

In practice: CPython uses reference counting plus a cycle detector for exactly this problem. Swift and Objective-C use reference counting and ask you to break cycles with "weak" references. The JVM, V8 and Go use tracing collectors (relatives of mark & sweep) that are generational (most objects die young, so the young area is checked often) and concurrent (they mark while your program runs) to keep pauses short.

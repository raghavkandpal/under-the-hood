HTTP/1.1, 2 and 3

A web page is dozens of files. Each version of HTTP found a better way to fetch them all at once, and HTTP/3 finally stopped one lost packet from holding up the rest.

How it works

HTTP/1.1. One connection carries one request at a time: ask, wait a round trip, get the file, ask for the next. Browsers open about six connections per site to fetch six files at once, and each new connection pays its own TCP and TLS handshakes first. Sites used to work around the limit by bundling files and spreading them over extra domains.

HTTP/2. One connection, many streams: the browser sends every request at once, and the responses come back interleaved in small frames. No more queuing behind six slots. But it all rides on one TCP byte stream, and TCP delivers bytes strictly in order. If one packet is lost, everything after it waits for the retransmission, even frames for other files that arrived fine. That's head-of-line blocking, and the more files are in flight, the more likely each round trip contains a loss.

Try it. Raise the loss to 10%. HTTP/2 falls behind HTTP/1.1, whose six separate connections each stall alone.

HTTP/3. QUIC moves the transport into user space on top of UDP, and keeps a separate order for each stream. A lost packet now delays only the file it belonged to. QUIC also merges the transport and TLS 1.3 handshakes into one round trip, and lets a phone switch from Wi-Fi to mobile data without starting over.

Simplified: time moves in round trips, files are small and equal, every lost packet costs one extra round trip, and congestion control is ignored. HTTP/2 also compresses headers, and HTTP/3 can resume known servers with no handshake at all.

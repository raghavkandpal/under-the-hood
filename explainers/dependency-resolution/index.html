Dependency resolution

Your app needs a web framework and a logger. They each need an HTTP library, but different versions of it. Every npm install, pip install and cargo build starts by solving this puzzle: pick one version of every package so that everyone's requirements hold at once.

How it works

  
Version ranges. Packages don't usually ask for one exact version. ^2.1.0 means “2.1.0 or anything newer before 3.0.0”, trusting that a change in the first number is a breaking one (semantic versioning). ~1.2.0 allows only patches, 1.2.x. Ranges give the resolver room to find versions everyone accepts.

  
Backtracking. The resolver tries the newest version of each package, adds that version's own requirements, and moves on. When two requirements can't both be met, it undoes its most recent choice and tries the next version down, exactly like a Sudoku solver. Here web 2.1 needs http 3, but every logger needs http 2, so it settles on web 2.0. In general this is NP-complete, which is why some installs take surprisingly long and why modern resolvers (pip, Cargo, Poetry, uv) use SAT-solver techniques.

  
Sometimes there's no answer. Add auth, which also needs http 3, and no single version of http satisfies everyone. A good resolver explains exactly which requirements clash. npm sidesteps the problem by nesting: each package gets its own copy of the version it wants. That never fails, but it can install the same library twice. That's usually fine, though it bloats the install, and it breaks when the two copies need to share state or types.

  
Lockfiles. Ranges mean the same package.json can install different versions next week, if a new release appears. A lockfile (package-lock.json, Cargo.lock, poetry.lock) records the exact versions that were resolved, so every machine and every deploy gets the same set until you deliberately update.

Leases and fencing tokens

A lock service grants a lease for ten seconds. The client holding it stalls for fifteen (a garbage-collection pause, a swapped-out VM), wakes up, and writes as if nothing happened. Meanwhile someone else has held the lock and written too.

    How it works

    Leases. A distributed lock can't wait forever for a holder that may have crashed, so it hands out leases: “the lock is yours for ten seconds; renew it or lose it”. If the holder dies, the lock frees itself. ZooKeeper, etcd and Consul all work this way, and so does leader election in Raft-based systems.

    The paused client. A lease only means something if the holder notices when it runs out, and a process can't notice anything while it's frozen. Garbage-collection pauses of several seconds, a VM being migrated, a laptop lid closing, or a network delay on the write itself all look the same: the client checks “do I still hold the lease?”, gets yes, stalls, and then acts on an answer that went stale while it slept. No amount of checking closes the gap, because the pause can come right after the check.

    Try it. Slide the pause up past the point where the lease runs out, then turn on fencing tokens.

    Fencing tokens. The fix is to let the storage decide. Each time the lock service grants the lease it hands out a number one higher than last time: the fencing token. Every write carries its token, and storage remembers the highest one it has accepted. A write with an older token is rejected, however confident its sender is. The zombie client's write bounces, and the data stays consistent.

    Where it applies. This only works if the storage can check tokens, so it needs cooperation from the database or service being protected. Many systems use the same idea under other names: Raft's term numbers, Kafka's leader epochs, and generation numbers in leader-elected services. A lock without fencing is a hint, not a guarantee.

    Simplified: one write per client, and clocks that agree. Leases also assume the lock service's clock and the client's run at about the same rate; a client whose clock runs slow can believe its lease lasts longer than it does.

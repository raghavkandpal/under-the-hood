System calls and interrupts

A program runs on the CPU with no way to touch the disk, the network or another program's memory. It has to ask the kernel, and the kernel has to be able to take the CPU back. Both depend on the same small mechanism: a CPU that can tell who is running.

Two modes

Privileged instructions. The CPU has a mode bit. In user mode, a few instructions are forbidden, such as the one that sets the trap table (lidt on x86). Running one is not an error the program can handle: the CPU traps into the kernel, which ends the process. In kernel mode the same instruction runs and changes the table. In this model the user run ends faulted and the table keeps its old entry; the kernel run points it at the new one.

Trap. A program asks for a service with a trap instruction (syscall on x86-64, with the call number in rax). The CPU flips to kernel mode and jumps to the handler address the kernel stored in the trap table at boot. The program cannot choose that address: set r2 to anything above and the entry is the same, because the kernel is only ever entered at a place it picked. The handler does its work, then a return-from-trap instruction flips back to user mode at the instruction after the trap. A user-mode write to the table is itself a privileged instruction, so it faults too. This is the mechanism OSTEP calls limited direct execution: the program runs directly on the CPU, limited to what the mode bit allows.

What a crossing costs

Fewer crossings. Writing 10,000 bytes one byte per write enters the kernel 10,000 times. A C program that writes through stdio gets a 4,096-byte buffer in user space: bytes are copied into it with no trap, and one write goes out each time it fills. That is 3 calls here: 4,096 bytes, 4,096 and the last 1,808 at the flush. Every byte arrives either way.

No crossing at all. Reading the clock needs no privilege, only the kernel's current time. On Linux the kernel maps a small page into every process, the vDSO, with code and data to read the time in user space (__vdso_clock_gettime on x86-64). In this model 1,000 clock reads enter the kernel 1,000 times as system calls and 0 times through the vDSO, with the same 1,000 times returned. This page gives no cost for a crossing: the model prices every instruction at 1 ms and the kernel's work at nothing, and that is not what hardware does.

Try it. Switch the writes between the two settings: the bytes written stay at 10,000 while the entries drop from 10,000 to 3.

Taking the CPU back

  • A
  • B

The timer. Two loops, A and B, never make a syscall and share 100 ms. Without help the kernel could never run again, because a program that does not call it does not give it the CPU. So at boot the kernel starts a timer that interrupts the CPU every 10 ms. Each interrupt enters the kernel through the trap table, and the kernel switches to the other loop (the scheduling page covers who to pick). With the 10 ms timer the kernel regains control 10 times and each loop runs 50 ms. With no timer the first loop runs all 100 ms and the second 0.

Waiting for a device. Process A reads from a disk that answers in 5 ms, while B loops. If the kernel blocks A and starts B, the disk interrupts the CPU when it is done, and B has run for those 5 ms. If A polls the device in a loop instead, A holds the CPU for the whole wait and B runs 0 ms of it: the 10 ms timer slice is longer than the 5 ms wait, so the timer never steps in. An interrupt lets the CPU do other work while a slow device is busy.

Try it. In the disk run, choose Poll and watch B's time in the wait fall from 5 ms to 0.

How a process is created or replaced is on the processes page; here a process is just a program counter, some registers and a state.

Simplified: one CPU, instructions of 1 ms, kernel work free, no nested interrupts, and a program that runs off its end exits. Polling is a loop on a status flag, and the call numbers and addresses are this model's own.

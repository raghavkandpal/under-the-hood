Text editor buffers

Typing one letter in the middle of a 100 MB log file should feel instant. Stored naively as one long string, every keystroke shifts every character after the cursor. Real editors use cleverer structures. Type below and watch two of them work.

Gap buffer (Emacs)

One array with a hole (striped) at the cursor. Typing fills the hole, which is free. Moving the cursor elsewhere slides the hole there, copying the characters in between.

Piece table (VS Code, Microsoft Word)

The original file is never touched. New text is appended to an “add” buffer, and the document is a list of pieces pointing into one buffer or the other.

How it works

The naive way. An array of characters is fine for short text. Insert at position p in a document of length n, though, and n − p characters shift right. Typing at the top of a large file costs the whole file per keystroke.

Gap buffer. Keep free space at the cursor. Typing writes into the gap and backspace widens it, both O(1). Moving the cursor costs the distance moved, but people mostly type in one place for a while. When the gap fills up, the buffer grows by doubling, an occasional big copy like a dynamic array's. Simple and fast, which is why Emacs has used one for decades. It struggles with multiple cursors far apart.

Piece table. Never move text at all. The original file can even stay memory-mapped on disk, and edits only append. An insert splits one piece into two and adds a new one between them. Undo is cheap, because old piece lists still describe old versions. VS Code stores its pieces in a balanced tree, so finding line 50,000 takes log time.

Ropes (Xi, Zed, many functional languages) are a third option: a balanced tree of short strings, good for huge files and concurrent edits.

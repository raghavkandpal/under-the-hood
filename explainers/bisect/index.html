Git bisect

The tests passed last month and fail today, and a thousand commits landed in between. Checking them one by one could take a thousand test runs. Bisecting takes ten.

    How it works

    Halving. You know one commit that's good and one that's bad, and the bug arrived at some commit in between. Test the one in the middle. If it's bad, the culprit is in the first half; if good, the second. Either way, half the suspects are cleared with one test. After k tests, 2k commits have been narrowed to one, so 1,024 commits take 10 tests and a million take 20. It's binary search over time.

    In git. git bisect start, mark the ends with git bisect bad and git bisect good <commit>, and git checks out the middle. Test, and answer good or bad. Better, hand it a script: git bisect run npm test does the whole search unattended, using the script's exit code as the answer.

    Try it. Run a search on 1,024 commits and count the tests. Then tick “Some don't build” and see what changes.

    Commits you can't test. Some commits in the middle won't build, or fail for an unrelated reason. git bisect skip sets one aside and tries a neighbour. If the skipped commits sit right next to the culprit, bisect can only say the bug arrived somewhere in a short range, and you read those commits yourself.

    What it needs. The test has to be reliable: a flaky test that sometimes fails on good commits sends the search the wrong way, and it never recovers. And the bug must have one arrival point, the classic “it worked, then it didn't”. Small, self-contained commits make the final answer more useful, since a giant merge commit as the culprit tells you little. Git's history of snapshots is what makes checking out any point cheap.

    Simplified: history is a straight line. In real git, merges make it a graph, and bisect picks commits that split the remaining suspects in half by count.

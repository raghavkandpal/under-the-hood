How debuggers work

A breakpoint looks like a pause button, but the CPU has no such thing. The debugger overwrites one byte of your program with a trap instruction, and has to put things back to carry on.

How it works

The trap byte. To set a breakpoint at address A, the debugger reads the byte there, keeps it, and writes 0xCC in its place. On x86 that is the one-byte INT3 instruction, so it fits over any instruction without touching its neighbours. On Linux the debugger does this with ptrace (PEEKTEXT and POKETEXT). Clearing the breakpoint writes the saved byte back, and the code is exactly as it was.

Rewinding. When the program runs into 0xCC the CPU has already moved on: the program counter is A + 1. The debugger reports A and sets the counter back. Turn Rewind off and the program resumes one byte past A: inside a longer instruction it runs an operand as an opcode, and a one-byte instruction is skipped. In this toy program that gives a different output at every address, or a crash.

Carrying on. The original instruction has to run once, but resuming as is would hit the 0xCC again. So the debugger puts the saved byte back, single-steps one instruction (PTRACE_SINGLESTEP), writes 0xCC again and resumes. A breakpoint in the 10-iteration loop then stops 10 times and the output is the same as without a debugger. Turn Re-arm off and the breakpoint fires once and is gone.

Try it. Turn on If i = 7. The program still traps 10 times, but you see only 1 stop. That is 20 switches into the debugger and back.

The cost of a condition. The CPU can't test i == 7 for you. The debugger stops the program every time, looks, and resumes if the condition is false. A conditional breakpoint in a hot loop is slow for that reason.

The VM is a made-up eleven-byte program, and a trap is counted as two switches whatever the operating system does. Real debuggers also handle signals, and other threads that could run past a breakpoint while its byte is lifted.

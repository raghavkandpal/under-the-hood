DNS resolution

Your computer knows blog.coffee.dev, but the network only routes to numbers. Here's how a name becomes an IP address. Nobody has the whole phone book. Each server just knows who to ask next.

    What's going on

    Your laptop runs a tiny stub resolver. It doesn't do the legwork. It asks one recursive resolver (your ISP's, or a public one) and waits.

    The recursive resolver starts at the root, which only knows who runs each top-level domain like .com. The TLD server only knows which nameservers each domain registered. The authoritative server for the domain finally holds the actual records.

    Every answer comes with a TTL (time to live), so the resolver can cache it. Delegations to TLDs last for days, so after one lookup the root is almost never asked again. Records like api.example.com (60s) expire quickly so operators can move them around. Even "doesn't exist" gets cached for a while. That's negative caching.

    Try it: look up api.example.com twice. The second lookup is instant. Press +5m and look again. Only the authoritative server gets asked, because the example.com NS entry is still fresh. Then try blog.coffee.dev, a CNAME chain that hops across three zones.

    All names, servers and addresses here are fictional (mostly from ranges reserved for documentation), and real resolvers add things this leaves out: glue records, DNSSEC, query minimisation, retries, and caching in your OS and browser.

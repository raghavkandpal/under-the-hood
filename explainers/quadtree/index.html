Spatial indexes

“Restaurants within 1 km”, “which enemies are near the player”, “which map tiles are on screen”. With a million points, checking each one on every query is far too slow. A quadtree carves space into boxes that split wherever things get crowded, so a query only looks inside the few boxes it overlaps.

Drag on the map to draw a search rectangle. Click without dragging to add a point. Keyboard: arrows move the rectangle, Alt + arrows resize it, Enter adds a point in its centre.

How it works

Split when crowded. Start with one box covering everything. When a box holds more points than its capacity, cut it into four equal quarters and hand its points down. Busy areas end up with tiny boxes many levels deep, and empty areas stay as one big box. The tree adapts to the data.

Querying. To find everything in a rectangle, start at the top. Any box that doesn't touch the rectangle is skipped along with everything inside it. Only points in the leaf boxes it overlaps are actually checked. For a small search area, that's a handful of boxes out of thousands, roughly logarithmic in the number of points.

Why not a simple grid? A fixed grid works well when points are spread evenly. Real data clusters: most of a map's restaurants are in a few cities, so one grid cell can hold thousands while most hold none. Switch to the grid view on clustered data and compare “points checked”.

Relatives: k-d trees (split on alternating axes, good for nearest-neighbour search), R-trees (boxes around shapes, used by PostGIS and SQLite), and geohashes and S2 cells, which turn 2-D positions into sortable 1-D keys that an ordinary B-tree can index. Games use the same idea for collision detection.

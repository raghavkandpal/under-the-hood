File systems

A disk is just a long row of numbered blocks. A file system turns that into names, folders and files that grow and shrink, and has to keep it all consistent when the power cuts out halfway through saving. Underneath every file is an inode, and names are just pointers to it.

How it works

Inodes hold the file; directories hold names. An inode records a file's size, its owner and permissions, and which blocks hold its data, but not its name. A directory is a small table of name → inode number. Opening /home/me/poem.txt means looking up “home” in the root directory, then “me”, then “poem.txt”. A bitmap tracks which blocks are free.

Hard vs symbolic links. A hard link is a second directory entry pointing at the same inode. Both names are equally real, and the data is only freed when the link count reaches zero. A symbolic link is a tiny file containing a path. Delete the target and the symlink dangles, pointing at nothing. Moving a file within a disk just edits directory entries, which is why it's instant even for huge files.

Crashes. Creating a file takes several separate writes: data blocks, bitmap, inode, directory entry. Lose power between them and the disk disagrees with itself: blocks marked used that no file owns, an inode nobody points to, or worse, a name pointing at garbage. In the past, every unclean shutdown meant a long fsck scan of the whole disk to find and repair such damage.

Journaling. First write the whole planned change to a log (the journal), then a commit record, and only then apply it. After a crash, replay committed entries and discard the rest. Either everything happened or nothing did. That's the write-ahead log idea, used by ext4, NTFS and APFS. Recovery takes seconds instead of a full scan.

Real file systems use larger blocks (usually 4 KB), journal only metadata by default, and newer ones like ZFS and Btrfs avoid overwriting anything in place (copy-on-write). Related: B-trees, used for large directories.

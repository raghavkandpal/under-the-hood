How a compiler works

Every program you run was text first. A compiler turns that text into instructions a machine can execute, through a pipeline of small, well-defined steps. Here's the whole pipeline for a tiny calculator language. Edit the code and every stage updates.

Try:

1. Lexer: text → tokens
2. Parser: tokens → syntax tree
3. Code generator: tree → bytecode
    4. Virtual machine: run it
    the stack

    What each stage does

    Lexing chops characters into meaningful chunks: numbers, names, operators. Spaces disappear, and 0.2 becomes one number token rather than three characters.

    Parsing checks the tokens follow the grammar and builds a tree. This is where 1 + 2 * 3 becomes "add 1 to (2 × 3)". The grammar has one rule per precedence level, so multiplication sits deeper than addition. It's a recursive-descent parser, the same technique used by many real compilers, including GCC's and Clang's C/C++ front ends.

    Code generation walks the tree and emits instructions for a stack machine: push the operands, then apply the operator. The order of the tree becomes the order of the code. Python, the JVM and WebAssembly all compile to stack-based bytecode like this.

    Optimisation rewrites the program to do less work without changing the result. Tick "constant folding": any sub-expression with no variables, like 2 - 1, is computed once at compile time. Real compilers run dozens of such passes.

    Grammar: assignments, + − × ÷ %, right-associative ^, unary minus and parentheses. Real compilers add type checking, many more optimisations, and register allocation when targeting real CPUs.

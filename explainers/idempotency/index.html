Idempotency keys

You tap Pay, the spinner spins, and the app says the network timed out. Did the payment go through? The app can't know either. If it simply tries again, some customers get charged twice.

One payment

    How it works

    The two failures look the same. If a request is lost on the way, the server never saw it, and retrying is exactly right. If the response is lost, the server already charged the card, and retrying charges it again. The client sees a timeout either way. Timeouts, dropped mobile connections, load balancers closing idle sockets and crashed clients all produce this, and automatic retries make it routine.

    Idempotent operations. An operation is idempotent if doing it twice has the same effect as doing it once. “Set the email to x” is; “add $20” isn't. HTTP's PUT and DELETE are meant to be idempotent and POST isn't, which is why browsers warn before resubmitting a form.

    Keys. To make a non-idempotent operation safe to retry, the client generates a unique key for each intended payment, and sends the same key with every retry. The server records each key with its result in the same database transaction as the charge. When a key arrives that it has seen, it skips the work and returns the stored result. Stripe's API and most payment systems work this way, through an Idempotency-Key header.

    Try it. Set request loss to zero and only lose responses, with and without keys. Then lose only requests.

    The details that matter. Two retries can arrive at the same moment, so the key needs a unique constraint or a lock, not a check-then-insert. Keys expire eventually (Stripe keeps them for 24 hours). And a retry that comes back with a different amount under the same key should be refused, not replayed.

    Simplified: each attempt independently loses its request or response, the client retries up to three times, and the server never crashes between charging and recording the key, which is why both go in one transaction.

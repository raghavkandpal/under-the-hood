Failure detection

A server stops answering. Has it crashed, or is the network just slow for a moment? From the outside the two look exactly the same, so every failure detector is a bet between noticing crashes fast and crying wolf.

How it works

Heartbeats. The usual way to watch a server is to have it send a small “still here” message every second and treat a long silence as death. Load balancers, clusters and consensus systems all do this. The question is how long a silence counts as long.

The trade-off. Heartbeats don't arrive exactly a second apart: they queue behind other traffic, and some get lost. A short timeout notices a real crash quickly, but every slow or dropped heartbeat becomes a false alarm, and each one can trigger a failover, a leader election or a page to whoever's on call. A long timeout is calm, but a dead server keeps receiving traffic for longer. No setting is right for every network.

Try it. With the fixed timeout, raise the jitter and watch the false alarms. Then switch to phi and do the same.

Phi accrual. Instead of a fixed number, the detector remembers how far apart recent heartbeats really were, and turns the current silence into a suspicion level, phi: how unlikely a gap this long would be on this network. Phi = 8 means a one-in-100-million gap. On a steady network the typical gap is tight, so suspicion rises quickly; on a jittery one the same phi waits longer. Cassandra and Akka use this.

Why it can't be perfect. In an asynchronous network there's no upper bound on delay, so no detector can be both always right and always eventually sure. That's a theorem, and it's why systems pair detectors with mechanisms that stay safe when a “dead” node turns out to be alive, like fencing tokens and quorum writes.

Simplified: a heartbeat a second, delays that only ever add to it, and phi computed from the last 100 gaps as if they were normally distributed. Real detectors also gossip suspicions between nodes.

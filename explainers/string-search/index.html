String searching

Ctrl+F looks simple: slide the word along the text and compare. The clever algorithms learn from each mismatch how far they can safely jump, and some barely read most of the text.

How it works

Naive. Line the pattern up at each position in turn and compare characters left to right until one differs. On ordinary text the first character usually differs, so it's fast. On repetitive text, like a run of a's with a b at the end, almost every alignment matches all but the last character, and the work becomes n × m.

Knuth–Morris–Pratt. When a mismatch comes after some matches, you already know what those text characters were: they were the start of the pattern. KMP precomputes, for each prefix of the pattern, how long a piece of it is also its own suffix. On a mismatch it shifts the pattern so that piece lines up, and carries on from the same text position. It never re-reads a text character it has passed, so it does at most about 2n comparisons whatever the input.

Boyer–Moore–Horspool. Compare from the pattern's end. If the text character under the last position doesn't occur in the pattern at all, nothing can match until you're past it, so jump the whole pattern length. Otherwise jump just far enough to line it up with its last occurrence in the pattern. With long patterns and a large alphabet most jumps are big, and it reads a fraction of the text: the longer the pattern, the faster the search. GNU grep is built on this idea.

Try it. On the sentence, search for a long word with Horspool and count how few columns get compared. Then switch to the repetitive text and compare all three.

Simplified: Horspool is the simple half of Boyer–Moore; the full algorithm adds a second, KMP-like shift rule. Real tools also use SIMD to compare many bytes at once, and automata like Aho–Corasick to search for many patterns together.

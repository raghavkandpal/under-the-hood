Sharding

When a table outgrows one machine, you split its rows across several. The rule that decides which row goes where looks like a detail, but it decides which queries stay fast, which machine melts, and how painful it is to add one more.

How it works

By range. Give each shard a slice of the key space: users 0 to 24,999 on the first, the next 25,000 on the second, and so on. Neighbouring keys live together, so “all orders from last Tuesday” or “users 4,000 to 4,500” is answered by one machine reading one contiguous run. Bigtable, HBase and CockroachDB split data this way.

The hot spot. Keys that grow over time, like auto-increment ids or timestamps, all land at the end of the key space. Every new signup goes to the last range shard while the others sit idle, so adding machines doesn't add write capacity. Range systems fight this by splitting busy ranges as they grow, or by prefixing keys so they don't sort in arrival order.

Try it. Pick new signups under each scheme, then a range scan under each.

By hash. Hash the key and take it modulo the number of shards. Similar keys scatter evenly, so sequential inserts spread across every machine. The price is locality: a range scan now has to ask every shard and merge the answers, and one slow shard slows every such query.

Adding a shard. With hash mod n, changing n moves almost every key: going from 4 to 5 shards moves about 80% of the data across the network. Range sharding only splits one slice. Consistent hashing fixes the hash case: a new shard takes over a fair share of keys and nothing else moves. Many systems also create many more small shards than machines up front, so growing means moving whole shards, not rehashing rows.

Simplified: 100,000 user ids, equal-sized ranges, and every operation costs the same. Real systems also have to rebalance while serving traffic and route each query to the right shard.

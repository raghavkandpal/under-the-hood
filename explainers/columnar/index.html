Column stores

An online shop's database writes one order at a time. Its analysts ask questions like “revenue by country this year” over 100 million orders, touching three columns of every row. Store the same table in a different order on disk and that question reads one-tenth of the data, compressed to a fraction of that again.

How it works

Same table, different order on disk. A row store (Postgres, MySQL) writes each record's fields together. That's perfect for “fetch order #42” or “insert a new order”: one place on disk. A column store (Parquet, ClickHouse, BigQuery) writes all the dates together, then all the countries, and so on. A query that needs 3 of 8 columns skips the rest entirely, and the skipped columns here include a wide free-text field.

Compression loves sameness. A column holds one type of data, often repetitive. Dates sorted by time become long runs (“2026-03-14 × 912”), which run-length encoding stores as one value and a count. Six countries become a dictionary of six strings plus a 1-byte code per row. A mostly-empty notes column almost vanishes. Rows mix types, so they compress far worse.

Fast CPUs on top. Looping over one tight array of prices suits CPU caches and SIMD instructions that process 8 or 16 values at once. Engines often compute directly on compressed data.

The trade-off. Single-row reads and writes are clumsy in a column store: inserting one order touches 8 separate places. So companies keep transactions in a row store (OLTP) and copy data periodically into a column store for analytics (OLAP). Some modern databases keep both layouts.

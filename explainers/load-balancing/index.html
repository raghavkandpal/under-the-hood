Load balancing

A load balancer hands each incoming request to one of many servers. The obvious strategies spread requests evenly, but "evenly" in number isn't evenly in work, and the unlucky requests pay for it in tail latency.

Four strategies

Random needs no state at all, but by pure chance some servers get a run of requests while others sit idle. That variation shows up directly in the p99.

Round robin gives each server exactly its turn, so request counts are perfectly even. But requests aren't equal. A server stuck on a long one keeps getting new requests queued behind it. Tick "heavy-tailed" to see how bad that gets.

Least connections sends each request to the server with the fewest in flight, so it adapts to slow requests and slow machines. It's the best here, but it needs an up-to-date view of every server, which is costly with many balancers and thousands of servers.

Power of two choices picks two servers at random and sends the request to the less busy one. That single extra look gets most of the benefit of checking every server. In theory, the worst queue shrinks from about log n / log log n to log log n. It's simple, scalable, and widely used (Nginx's "random two", Envoy, many service meshes).

Each run sends 20,000 requests with random (Poisson) arrivals. Request sizes are exponential, or 95% tiny and 5% about 14× the average when heavy-tailed. Every server processes one request at a time, first come first served. The first 10% of requests are discarded as warm-up.

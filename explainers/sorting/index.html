What to notice

n² vs n log n. Bubble, insertion and selection sort compare roughly every pair, about n²/2 operations. Merge, quick and heap sort split the problem in halves, about n·log₂n. At n = 300 that's ~45,000 against ~2,500. At a million items it's the difference between seconds and days.

Input matters. On nearly sorted data, insertion sort finishes almost immediately, because each item only moves a step or two. That's why real libraries switch to it for small or almost-ordered chunks. Selection sort doesn't care and always does all n²/2 comparisons.

Trade-offs among the fast ones. Merge sort is predictable and stable (equal items keep their order) but needs extra memory. Quicksort is usually fastest in practice thanks to cache-friendly access, but can degrade to n² on unlucky pivots; this one uses median-of-three to dodge the easy traps. Heapsort guarantees n log n in place, but jumps around memory.

What real languages use: Python and Java (for objects) use Timsort, a merge/insertion hybrid that exploits existing runs. C++ std::sort and Rust's unstable sort use introsort-style quicksorts that fall back to heapsort.

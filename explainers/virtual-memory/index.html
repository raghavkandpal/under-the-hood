Virtual memory

Every program believes it has the whole memory to itself, starting at address 0. That's an illusion the CPU and operating system maintain together, translating every address on every access, and quietly moving pages to and from disk when real memory runs out.

How it works

Pages and frames. Memory is cut into fixed-size pages (here 256 bytes, 4 KB on most real systems). An address splits into a page number and an offset within the page. The page table maps each virtual page to a physical frame, and the offset carries over unchanged.

The TLB. The page table lives in memory, so consulting it on every access would double the cost of everything. The CPU caches recent translations in a tiny, very fast TLB. Programs that touch several addresses on a page before moving on get mostly free translation (see "Loop over 3 pages"). Shrink the TLB to 1 entry and the hit rate drops, because every page switch evicts the last translation.

Page faults. If a page isn't in memory, the CPU traps to the operating system, which loads it from disk into a free frame. If no frame is free, it evicts a victim. Disk is roughly 100,000× slower than RAM, so the choice of victim matters. LRU evicts what hasn't been touched for longest. FIFO evicts what was loaded earliest, which is simpler but blind to use.

Thrashing. When a program's working set is bigger than memory, every access can evict the page needed next. "Loop over 5 pages" with 4 frames faults on every access under LRU. Give it 5 frames and it faults only the first five times. That cliff is why a machine that starts swapping suddenly becomes unusable.

Toy scale: 256-byte pages, 16 virtual pages, up to 6 frames. Real systems use multi-level page tables, hardware dirty and accessed bits, and approximations of LRU like the clock algorithm. Each process also gets its own page table, which is how processes are isolated from each other.

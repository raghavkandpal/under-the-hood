HTTP caching

The fastest request is the one never made. A few response headers decide whether your browser reuses a file, asks "has this changed?", or downloads it all again, and whether a CDN answers on the server's behalf. Get them wrong and users either wait for nothing or see yesterday's site.

How it works

Fresh means "don't even ask". Cache-Control: max-age=60 lets the browser reuse its copy for 60 seconds with no network at all, which is the fastest possible load. CDNs (shared caches) can be given their own lifetime with s-maxage.

Stale means "ask, cheaply". After it expires, a browser holding an ETag sends If-None-Match. If nothing changed, the answer is a tiny 304 Not Modified, a round trip with no body. Without an ETag (or Last-Modified), it has to download everything again.

The catch: long lifetimes hide deploys. Set max-age to 1 hour, load, then deploy. You keep seeing the old version (red) until the hour is up, and nothing on the server can reach into your cache to fix it. The standard fix is cache busting: put a content hash in the file name (app.3f9a1c.js), cache it "forever", and change the name on every deploy. The HTML that references it gets a short max-age or no-cache.

no-store is for things that must never be kept, like a bank statement. no-cache, confusingly, means "store it, but revalidate every time".

Simplified model of RFC 9111: one browser per user, one CDN shared by everyone, a 200 KB file, roughly 20 ms to the CDN and 150 ms to the origin.

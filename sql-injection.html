SQL injection

A login form asks a database: “find the user with this name and this password”. If the program builds that question by pasting your typing into the middle of it, then your typing can change the question. One of the oldest bugs on the web, still near the top of every security list, and fixed by a one-line change.

How it works

Code and data in one string. The vulnerable program writes "… WHERE username = '" + name + "' AND …". The database receives one block of text and has to work out which parts are instructions and which are values. A quote mark in your name ends the value early, and everything after it is parsed as SQL.

The classic. Type ' OR '1'='1' -- as the username. The quote closes the string, OR '1'='1' is true for every row, and -- turns the password check into a comment. The database dutifully returns every user, and the app logs you in as the first one. alice' -- is quieter: it logs in as one chosen account without knowing her password.

It's not only attackers. A customer called O'Brien breaks the same query by accident. Escaping quotes by hand seems to help, but it's easy to get wrong across character sets, numbers and edge cases.

The fix: parameterised queries. Send the SQL with ? placeholders, and the values separately. The database parses the query before it sees your input, so the input can only ever fill a value slot, whatever characters it contains. Every database library supports this (db.query(sql, [name, pass])), and ORMs do it for you.

Simplified: a tiny SQL subset and an in-memory table. Real systems also store password hashes, never passwords, and give the app's database account only the permissions it needs, so a successful injection can do less damage.

How diff works

Every code review, git diff and "track changes" view answers the same question: what's the smallest set of deletions and insertions that turns the old version into the new one? The answer is a grid and a shortest path.

The diff
The edit graph old runs down the side, new across the top. Moving right inserts, moving down deletes, and a diagonal (only where the two match) keeps a free character. The diff is the path with the most diagonals.

What's going on

Longest common subsequence. Find the longest sequence of items that appears in both versions in the same order. Those stay put, and everything else is a deletion (from old) or an insertion (into new). Fewer kept items means a bigger, noisier diff.

Dynamic programming. Fill a table where each cell holds the best answer for the remaining parts of both inputs, built from its neighbours: if a[i] = b[j] then 1 + diag else max(right, down). Then walk from the top-left, taking diagonals when allowed. It's O(n·m), fine for a page of text, slow for two 100,000-line files.

What git actually does. Git uses Myers' algorithm (1986), which finds the same shortest edit path but explores only as far as needed, in O((n+m)·D) time where D is the size of the diff. Small changes to huge files are fast. Variants like "patience" and "histogram" diff anchor on unique lines first, which often produces diffs people find easier to read, even when they aren't the strict minimum.

Granularity matters. Switch between characters, words and lines on the same text. Code review tools diff by line, then highlight words within changed lines, for exactly this reason.

Ties are broken by preferring deletions before insertions, as most tools do. The edit graph is drawn only when both sides are short enough to fit.

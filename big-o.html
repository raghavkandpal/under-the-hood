Big-O notation

Two programs both handle 100 items in a blink. At a million items one still takes a blink and the other takes a week. Big-O describes how the work grows as the input grows, which matters far more than how fast your computer is. Drag n and watch the classes pull apart.

How it works

Count steps, not seconds. Seconds depend on the machine. Instead count basic operations, such as comparisons or loop turns, as a function of input size n. Big-O keeps only the fastest-growing part and drops constants: 3n² + 5n + 100 is O(n²), because at large n the n² term is all that matters.

The usual suspects. O(1): same work at any size, like reading an array slot or a hash table lookup. O(log n): halve the problem each step, like binary search, where a million items take 20 steps and a billion take 30. O(n): look at everything once. O(n log n): the best possible for comparison sorting. O(n²): every pair, fine for hundreds, painful for millions. O(2ⁿ): every subset, hopeless past about 50.

Doubling tells you the class. Double n: O(1) work stays the same, O(log n) gains one step, O(n) doubles, O(n²) quadruples, O(2ⁿ) squares. Measuring how runtime changes when input doubles is a quick way to spot an accidental O(n²) in real code.

Small n can fool you. On the plot, at tiny sizes the curves overlap and constants matter. That's why real sort functions switch to simple O(n²) insertion sort for small pieces. Big-O is about the long run.

Step counts here come from actually running each algorithm up to n = 20,000, and from their exact formulas beyond that. Times assume a billion steps per second.

Vector clocks

Three servers each have their own clock, and the clocks disagree. When two of them change the same data, which change came first? Sometimes there's an answer. Sometimes the honest answer is "neither: they happened concurrently". Vector clocks can tell those cases apart.

How it works

Happens-before. Event a happened before b if information could have flowed from a to b: same server and earlier, or a message chain connects them. If neither could have reached the other, they're concurrent. Neither saw the other, so neither "wins" by default, and two such writes to the same key are a genuine conflict.

A vector clock keeps one counter per server. Each server ticks its own counter at every event and stamps outgoing messages with its whole vector. On receiving one, it takes the element-wise maximum, then ticks. Then a → b exactly when a's vector is ≤ b's in every position. If each is bigger somewhere, they're concurrent.

Lamport clocks are the one-number version. They guarantee that if a → b then L(a) < L(b), but not the converse. Switch the labels and find two concurrent events with different Lamport numbers. The smaller number looks "earlier", but that's an illusion. That's why systems that must detect conflicts, like Dynamo-style databases and some sync engines, carry vectors.

Messages here are delivered instantly in the order you click. The price of vector clocks is size: one counter per participant, which is why large systems prune them or use variants like dotted version vectors.
